Sign / Verify

Sign text with a security key or a private key, then verify it check by check

A WebAuthn assertion never signs your bytes directly — it signs authenticatorData ‖ SHA-256(clientDataJSON). To sign a message with a security key, its hash goes in the challenge; verification re-derives that hash and checks it matches. That one step is what binds the signature to the content.

A compact JWS, or a WebAuthn authentication response in JSON — whichever you have. The format is detected.
Neither format carries a public key, and that is deliberate: a signature that ships its own key proves the bytes are intact but nothing about who signed them. The key has to come from you. (HS256 uses the shared key below instead.)
The domain the signature was made for. It is checked against rpIdHash — a WebAuthn assertion is bound to it and cannot be replayed as one made elsewhere.
WebAuthn §7.2 requires a verifier to check clientDataJSON.origin, not just the RP ID: the RP ID fixes the host, but only the origin fixes the scheme and port. Without this an assertion produced on a different origin under the same host would pass.

Verification checklist
What a security-key signature does and does not prove
  • Only FIDO2-aware verifiers can check it. The signature covers the WebAuthn structure, so it is not a PGP, CMS/S-MIME, JWS, or PAdES signature and no such tool will accept it. That is why the output here is the WebAuthn authentication response JSON — the shape every FIDO2 server already parses — rather than an invented one. Signing with a private key instead produces a plain compact JWS, which any JOSE library reads. Note a JWS is not automatically a JWT: JWT requires a JSON payload, so only a JSON message makes the token readable by JWT tooling — including this site’s JWT Encode / Decode.
  • It is bound to a domain. rpIdHash commits to the site that requested it — a signature made here says “made on this origin”, and cannot be replayed as one made elsewhere.
  • The signature counter is not non-repudiation. It exists for clone detection; 0 is normal for platform passkeys.
  • There is no raw-hash signing in browsers yet. The WebAuthn sign extension is still a W3C draft, and YubiKey’s previewSign (firmware 5.8, CTAP 2.3) is explicitly early-access and unsupported by browsers.
  • HS256 is a MAC, not a signature. Anyone who can verify it could also have produced it, so it proves integrity between people who already share a secret — nothing more.
  • These assertions are not logins, and must never be accepted as one. WebAuthn §13.4.3 requires an authentication challenge to be freshly random; here the challenge is SHA-256(message), which is deterministic on purpose. So an assertion produced here carries no freshness and is replayable as an authentication assertion against any server careless enough to accept a challenge it did not generate. Treat the output as a document signature only.
  • The credential is shared across the whole host. The RP ID is the entire subdomain under *.github.io style hosting, so every page under that host sees the same credential.
  • Verification here is stateless. A real Relying Party also stores a credential record and compares the signature counter and backup state against it across ceremonies (§7.2 steps 6, 19, 22). With nothing but a pasted public key there is no history to compare, so clone detection is out of scope.
