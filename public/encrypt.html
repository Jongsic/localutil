What comes out, and why it is split

The ciphertext is nothing but AES-256-GCM output — no header, no marker, nothing that says how it was produced. The derivation parameters come out separately, to be agreed out of band. They are still authenticated as the GCM additional data, so presenting different parameters fails instead of decrypting to garbage.

  • Security key — WebAuthn PRF (CTAP2 hmac-secret) output → HKDF-SHA-256. Parameters: credential id, salt. The credential is created non-discoverable, so it occupies none of the key’s credential slots; naming it by id at assertion time is enough.
  • Password — PBKDF2-HMAC-SHA-256, 600,000 iterations. Parameters: salt, iteration count, so it can be raised later.
  • Raw key — 32 bytes of hex or base64 → HKDF-SHA-256. Parameters: salt.
  • Public key — EC (P-256/384/521) uses ephemeral-static ECDH-ES + HKDF, so only an ephemeral public key travels. RSA-OAEP-SHA-256 is the one case that cannot agree on a key and must carry a wrapped one.

The parameters are the GCM additional data, built in a fixed field order with every name and value length-prefixed. Reordering the lines or changing their spacing is harmless; changing a value — swapping a salt, lowering the PBKDF2 count — makes decryption fail instead of silently weakening the result. Values are bound exactly as written, so re-padding a base64 value (AAAA vs AAAA=) also fails: pass them through unaltered. File names are never stored.
