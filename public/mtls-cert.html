mTLS Cert Issuer

Create a CA and issue client certificates from it for mutual TLS — .crt, .key and a password-protected .p12

What comes out
A CA certificate for the server side to trust, and client certificates signed by it — as .crt, .key, and a password-protected .p12. Keys are generated by your browser's own crypto and never leave this page.
1Certificate authority
The CA certificate is the public half — whatever verifies the client certificates has to trust it. The CA private key stays here; it is only used to sign, and nothing else ever needs a copy.
Set once, here. It encrypts the downloaded ca.key (PKCS#8, AES-256) and is what you will be asked for if you load that key back later.

Encrypted PKCS#8 (BEGIN ENCRYPTED PRIVATE KEY) and traditional OpenSSL keys (Proc-Type: 4,ENCRYPTED) are both read. RSA keys only.
2Client certificate
The subject is how the other side tells this client apart from the next one — most servers hand it to the application verbatim. Name the client something you can match on.
Each entry is typed by its shape: an IP address becomes an IP SAN, an address holding an @ becomes an email SAN, anything holding :// a URI SAN, and everything else a DNS SAN.
Advanced
For a certificate that has to answer in both directions — the extended key usage becomes clientAuth, serverAuth.
Every certificate is signed sha256WithRSAEncryption, carries a random 128-bit serial and subject / authority key identifiers, and is back-dated five minutes for clock skew. Extensions: basicConstraints CA:FALSE, keyUsage digitalSignature, keyEncipherment, extKeyUsage clientAuth.
3Issue
client.key comes out as encrypted PKCS#8 instead of plaintext. Ignored when the password is blank.
